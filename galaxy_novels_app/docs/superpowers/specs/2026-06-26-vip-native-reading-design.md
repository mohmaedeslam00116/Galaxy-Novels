# تصميم نظام VIP للقراءة الأصلية

## القرار المعتمد

ننفذ نظام VIP داخل تطبيق Galaxy Novels كمرحلة قراءة فقط. الهدف أن يعرف التطبيق حالة اشتراك المستخدم، يعرض فصول VIP عند السماح، ويفتح الفصل داخل القارئ الأصلي Native Reader بدون WebView.

الشراء والدفع والمتجر مؤجلة بالكامل في هذه المرحلة. لا نضيف checkout، ولا PayPal، ولا صفحة متجر فعالة، ولا زر شراء مباشر داخل التطبيق.

## الأهداف

- عرض حالة VIP في الحساب بشكل واضح: فعال أو غير فعال، اسم الباقة إن وجد، وتاريخ الانتهاء إن وجد.
- عرض حالة VIP داخل تفاصيل الرواية اعتمادا على `GET /me/novels/{novel_id}`.
- جلب فصول VIP للمستخدم المصرح له من `GET /vip/chapters`.
- فتح فصل VIP داخل القارئ الأصلي الحالي، بنفس تجربة القراءة وإعداداتها.
- دعم الانتقال للفصل التالي الخاص عبر `GET /vip/continuous-next`.
- حماية تجربة المستخدم عند انتهاء الجلسة أو عدم وجود اشتراك.
- إبقاء محتوى VIP خارج التنزيلات والكاش الدائم.

## خارج النطاق

- شراء الاشتراكات أو الدفع داخل التطبيق.
- تفعيل PayPal أو أي بوابة دفع.
- صفحة Store كاملة.
- تنزيل فصول VIP للقراءة دون إنترنت.
- نظام نقاط أو إعلانات مرتبط بالـ VIP.
- تغيير backend أو تعديل قالب WordPress في هذه المرحلة.

## API المستخدم

كل الطلبات الخاصة تستخدم `PrivateApiClient` الحالي وترسل:

- `Authorization: Bearer ACCESS_TOKEN`
- `X-Wor-App-Token: ACCESS_TOKEN`
- `User-Agent: WorReaderApp/1.0 Android`
- `Cache-Control: no-store`

المسارات المعتمدة:

- `GET /me`: يعيد حالة الحساب وبيانات `vip`.
- `GET /me/novels/{novel_id}`: يعيد حالة المستخدم للرواية و`vip.can_read_private`.
- `GET /vip/chapters?novel_id={id}&limit=...&order=...&cursor_order=...&cursor_id=...&search=...`: يعيد قائمة فصول VIP المتاحة.
- `GET /vip/continuous-next?chapter_id={id}`: يعيد HTML الفصل التالي الخاص إذا كان متاحا.
- `POST /vip/library-counts`: اختياري لاحقا لحسابات المكتبة، وليس مطلوبا لأول تنفيذ.

## النماذج المقترحة

### `VipChapter`

يمثل صف فصل VIP في تفاصيل الرواية:

- `id`
- `number`
- `position`
- `order`
- `title`
- `url`
- `publicAt`
- `views`
- `comments`

يعتمد على نتيجة `GET /vip/chapters`.

### `VipChapterPage`

يمثل صفحة نتائج قابلة للتمرير:

- `items`
- `hasMore`
- `nextCursorOrder`
- `nextCursorId`
- `totalAvailable`

### `VipReaderChapterContent`

لا نحتاج صنفا منفصلا لو استطعنا تحويل استجابة VIP إلى `ReaderChapterContent`. الأفضل أن يبقى القارئ يتعامل مع نموذج واحد.

## طبقة البيانات

نضيف مستودعا مستقلا:

`PrivateVipRepository`

مسؤولياته:

- جلب قائمة فصول VIP لرواية.
- تحويل أخطاء `401` و`403` إلى حالات مفهومة للواجهة.
- جلب الفصل التالي الخاص وتحويل استجابة `html` إلى `ReaderChapterContent`.
- عدم حفظ محتوى الفصل الخاص في أي تخزين دائم.

لا يحق للمستودع أن يستخدم `PublicCacheClient`، لأن بيانات VIP خاصة وغير قابلة للكاش العام.

## ربط القارئ الأصلي

القارئ الحالي يعتمد على `ReaderRepository.loadChapter(contentApi)`.

التصميم المقترح:

- إنشاء `HybridReaderRepository`.
- إذا كان `contentApi` يبدأ بـ `/wp-json/wor-reader-app/v1/vip/continuous-next` أو يحمل علامة `vip:` داخل التطبيق، يوجه الطلب إلى `PrivateVipRepository`.
- غير ذلك يمرر الطلب إلى `PublicReaderRepository`.

بهذا لا تتضخم `ReaderScreen` ولا يعرف تفاصيل public/private. الشاشة تستمر في فتح `ReaderChapterContent` واحد.

## فتح أول فصل VIP

`GET /vip/chapters` يعيد قائمة الفصول لكنه لا يعيد `content_api` مباشر. لذلك عند ضغط فصل VIP:

1. ننشئ مسار قراءة خاص داخلي مثل:
   `vip:chapter:{chapter_id}`
2. `HybridReaderRepository` يفسر هذا المسار.
3. المستودع يطلب محتوى الفصل الخاص من مسار مناسب.

إذا كان القالب لا يملك مسار direct content للفصل الأول، نستخدم `GET /vip/continuous-next?chapter_id={previous_or_current}` فقط عندما يكون الفصل الحالي معروفا. لكن هذا لا يكفي لفتح أول فصل من القائمة مباشرة. لذلك قبل التنفيذ يجب اختبار استجابة `GET /vip/chapters` على حساب VIP حقيقي:

- إذا كانت تحتوي رابط قراءة خاص أو حقل content مناسب، نستعمله.
- إذا كانت لا تحتوي إلا metadata، نحتاج إضافة alias صغير في القالب لاحقا مثل:
  `GET /vip/chapter?chapter_id={id}`

هذا ليس تغييرا مؤكدا الآن، لكنه نقطة تحقق إلزامية قبل تنفيذ فتح الفصل الأول.

## واجهة تفاصيل الرواية

نضيف قسم VIP منفصل عن الفصول العامة:

- يظهر بعد الفصول العامة أو كتبديل واضح بين "الفصول" و"VIP".
- إذا المستخدم ضيف: رسالة مختصرة تطلب تسجيل الدخول لمعرفة حالة VIP.
- إذا المستخدم مسجل وغير VIP: رسالة أن الفصول خاصة بالمشتركين، بدون زر شراء.
- إذا المستخدم VIP: قائمة فصول VIP مع بحث وترتيب وتحميل كسول.

لا نخلط فصول VIP داخل قائمة الفصول العامة حتى لا يظن المستخدم أنها فصول عامة قابلة للتنزيل.

## الحساب

الحساب يستخدم `AuthUser.vip` الموجود حاليا:

- إذا `active = true`: شارة VIP مع `label`.
- إذا `expiresAt` موجود: عرض تاريخ الانتهاء بصيغة مفهومة.
- إذا غير فعال: عرض حالة عادية بدون دعوة شراء كبيرة، لأن الدفع مؤجل.

## التنزيلات

فصول VIP ممنوعة من التنزيل في هذه المرحلة.

الأسباب:

- API يعلنها private/no-store.
- الاشتراك قد ينتهي.
- لا توجد سياسة حذف مرتبطة بانتهاء الاشتراك.
- لا نريد تخزين محتوى خاص في ملفات الجهاز قبل تصميم حماية واضحة.

واجهة الفصل الخاص لا تعرض زر تنزيل. لو ظهر من مكون مشترك يجب تعطيله برسالة: "فصول VIP غير متاحة للتنزيل حاليا".

## السجل ونشاط القراءة

عند قراءة فصل VIP:

- نسجل السجل المحلي مثل الفصول العامة إذا كان لدينا `novelId`, `chapterId`, `position`, `total`.
- نرسل نشاط القراءة بنفس الآلية الحالية إذا كان المستخدم مسجلا.
- لا نحفظ HTML الفصل داخل السجل.

إذا لم نستطع معرفة `total` بدقة من استجابة VIP، نستخدم `totalAvailable` من قائمة VIP أو سياق الفصل القادم، ولا نخترع نسبة تقدم.

## حالات الخطأ

- `401`: الجلسة انتهت أو المستخدم غير مسجل. نطلب استعادة الجلسة، ثم نعرض دعوة تسجيل الدخول إذا بقي الخطأ.
- `403`: لا يوجد اشتراك فعال. نعرض رسالة أن الفصل يحتاج VIP.
- `404`: الفصل غير متاح أو لا يوجد فصل تال. نعرض رسالة هادئة داخل القارئ.
- فشل الشبكة: زر إعادة المحاولة، بدون fallback إلى كاش قديم.
- JSON غير متوقع: رسالة تعذر تحميل فصول VIP مع تسجيل آمن في debug فقط.

## الأداء

- جلب فصول VIP يتم عند فتح قسم VIP فقط.
- حد الصفحة الافتراضي 50 فصلا.
- لا shimmer ثقيل ولا animations مستمرة.
- يمكن استخدام loading بسيط و`AnimatedSwitcher` خفيف عند تبديل حالات القسم.
- لا تحميل مسبق لمحتوى الفصول الخاصة.

## الاختبارات

اختبارات وحدة:

- parsing لـ `VipChapter` و`VipChapterPage`.
- `PrivateVipRepository` يرسل Bearer token عبر `PrivateApiClient`.
- `403` يتحول إلى حالة "اشتراك مطلوب".
- `401` يتحول إلى حالة "تسجيل دخول مطلوب".
- `HybridReaderRepository` يوجه public إلى public وVIP إلى private.

اختبارات Widgets:

- تفاصيل الرواية تعرض رسالة ضيف عند عدم تسجيل الدخول.
- تفاصيل الرواية تعرض رسالة غير مشترك عند `canReadPrivate = false`.
- تفاصيل الرواية تعرض قائمة VIP عند `canReadPrivate = true`.
- زر تنزيل لا يظهر أو يتعطل لفصول VIP.
- القارئ يفتح محتوى VIP المحول إلى `ReaderChapterContent`.

اختبارات يدوية:

- حساب غير مسجل: فتح تفاصيل رواية فيها VIP يظهر تنبيه تسجيل الدخول.
- حساب مسجل غير VIP: يظهر أن الفصول تحتاج اشتراكا ولا يظهر شراء.
- حساب VIP: تظهر فصول VIP وتفتح في القارئ الأصلي.
- انتهاء الجلسة: يعود التطبيق لحالة تسجيل الدخول دون فقدان الشاشة العامة.
- التنزيلات: لا يمكن تنزيل فصل VIP.

## نقاط تحقق قبل التنفيذ

قبل كتابة الكود النهائي لفتح فصل VIP مباشر يجب تجربة `GET /vip/chapters` بحساب VIP فعلي ومعرفة هل الاستجابة تحتوي ما يكفي لطلب محتوى الفصل الأول. إذا لم توجد وسيلة مباشرة، سنحتاج طلب تعديل صغير في القالب لإضافة مسار:

`GET /wp-json/wor-reader-app/v1/vip/chapter?chapter_id={id}`

هذا المسار يجب أن يعيد نفس شكل `ReaderChapterContent` العام تقريبا، لكن مع `Cache-Control: private, no-store`.

## تعريف النجاح

- يستطيع مستخدم VIP رؤية فصوله الخاصة وقراءتها داخل القارئ الأصلي.
- غير VIP لا يرى محتوى خاص ولا يحصل على تجربة مكسورة.
- لا توجد أي بوابة دفع أو شراء في هذه المرحلة.
- لا يتم تنزيل أو كاش محتوى VIP بشكل دائم.
- جميع اختبارات Flutter تمر: `flutter analyze`, `flutter test`, و`flutter build apk --debug`.
